## エージェントを信じるな。システムを信じよ。

**noomoo は、エージェントによるソフトウェア開発のためのエンジニアリング・ハーネスです。**

コーディングエージェントに、チームが実際に強制できるルールの範囲内で、計画・実装・テスト・レビュー・リリースを任せられます。

noomoo は、エージェントが「やった」と言うことを信じるのではなく、リポジトリで実際に何が起きたかを確認します。

AI 支援のコーディングから自律的なソフトウェアデリバリーへ移行するチームのために作られています。

## AI でコードは安くなった。新たなボトルネックは検証だ。

コーディングエージェントはすでに、機能の実装、バグ修正、テストの実行、pull request の作成、レビューへの対応までこなします。もはや問題は「**エージェントにコードが書けるか**」ではありません。本当の問いはこうです。

- 要件を理解したか？
- タスクの範囲内にとどまったか？
- アーキテクチャに従ったか？
- 本当にテストを追加したか？
- そのテストは本当に実行されたか？
- 最新の変更の後も、レビューはまだ有効か？
- 「完了」は事実か、それともエージェントがそう言っただけか？

## エージェントは口先でゲートを通り抜けられない。

| エージェント | noomoo |
|---|---|
| 「すべてのテストが通りました。」 | **このリビジョンのテスト結果を見せてください。** |
| 「変更をレビューしました。」 | **現在のコードに対する最新のレビュー成果物を見せてください。** |
| 「タスクで求められた部分だけを変更しました。」 | **差分を見せて、範囲を証明してください。** |
| 「タスクは完了しました。」 | **証明してください。** |

自然言語で書かれた状況報告は証拠ではありません。**リポジトリの状態こそが証拠です。**

## 人が舵を取り、エージェントが実行し、noomoo が検証する。

1. **成果を定義する。** 要件・ユースケース・機能・タスクが追跡可能なチェーンを形作ります。タスクが示すのは**何が真でなければならないか**であり、エージェントがどうコードを書くべきかではありません。
2. **タスクが実行可能であることを証明する。** 作業を始める前に、noomoo は構造・境界・リンク・曖昧さを確認します。推測なしに実行できないタスクなら、作業は始まりません。
3. **コードを変える前に計画する。** 実装計画は、実装・契約・テスト・決定を網羅する、バージョン管理された成果物になります。
4. **エージェントに作業させる。** コーディングエージェントは、隔離されたブランチまたは worktree で実装・テスト・レビュー・修正を行い、デリバリーを準備します。
5. **実際に何が起きたかを検証する。** noomoo は Git、ファイル、AST、テスト、レビュー成果物、CI、プロジェクト固有の不変条件を確認します。
6. **証拠があるときだけ先へ進む。** 必要な事実がそろっていれば作業は進み、そろっていなければ止まります。

## 指示は導くだけ。noomoo は強制する。

`CLAUDE.md`、`AGENTS.md`、プロンプト、スキルは役に立ちます。しかしそれらは、エージェントが読み、覚え、解釈し、従うことに依存したままです。noomoo はそれらを補完します。

CI はコードがビルドできるか、テストが通るかを教えてくれます。**CI はコードを確認し、noomoo はその周りの開発ライフサイクルを確認します。**

**エージェントにもっと仕事を任せよう。ただし、自分の宿題を自分で採点させるのはやめよう。**

## Claude Code 向け noomoo

noomoo は、コーディングエージェントのためのエンジニアリング統制レイヤーです。エージェントの言うことを信じるのではなく、リポジトリで実際に何が起きたかを確認します。ドキュメント、Git、テスト、CI に対する決定論的なチェック、現在のリビジョンに結び付いたライフサイクルゲート、レビューの状態、プロジェクトのステータスです。

このプラグインは、noomoo のワークフローをスキルとして Claude Code に持ち込みます。各スキルは、プロジェクトにインストールされた noomoo コアパッケージを呼び出します。検証と受け入れの拠り所はコアです。作業フェーズを閉じるのはコアコマンドの終了コードであり、エージェントの報告ではありません。このプラグインは Git、テスト、CI、リポジトリのポリシーに取って代わるものではありません。

## 必要なもの

プラグインはコアをインストールしません。noomoo パッケージは各プロジェクトにご自身で追加してください。パッケージがない場合、スキルはインストールを求めて停止します。

- Node.js 20 以降と Git。
- プロジェクトがすでに使っているパッケージマネージャーで追加した noomoo コアパッケージ:

```bash
npm install -D noomoo
pnpm add -D noomoo
yarn add -D noomoo
bun add -d noomoo
```

- サインイン済みの GitHub CLI（`gh`）。`/noomoo:task` のうち、pull request、その CI 実行、レビュアーの身元を読み取るステップで使います。

Superpowers は任意です。インストールされていれば、`/noomoo:task` は設計、テスト駆動の実装、レビュー、検証をそのスキルに委ねます。なければ、スキルが同じフェーズを自ら進めます。どちらの経路でも、各フェーズは同じコアコマンドで閉じられます。

## はじめに

1. 上記のとおりコアパッケージをインストールします。
2. Claude Code で `/noomoo:setup` を実行します。インストール計画を表示し、確認するまで何も変更しません。ターミナルからも同じです。`npx --no-install noomoo setup` は計画を表示し、`npx --no-install noomoo setup --yes` は計画を適用して `.noomoo/setup-manifest.json` に記録します。
3. `chore/noomoo-setup` のようなサービスブランチから、専用の pull request でインストールをメインブランチに取り込みます。
4. `/noomoo:start` を実行して、プロジェクトの現在地と次にやることを確認します。

`/noomoo:rollback` はマニフェストに基づいてインストールを取り除きます。まず計画を表示し、セットアップ後に変更したファイルは残します。

## アイデアから pull request まで

noomoo はデリバリーの流れ全体をカバーし、各ステップは次のステップが確認するドキュメントか事実を残します。

1. **Intake。** `/noomoo:intake` は生の素材をオーナー向けの提案にまとめます。
2. **仕様。** `/noomoo:spec` は作業を追跡可能なチェーンとして記述します: 要件 → ユースケース → 機能 → タスク。
3. **設計。** `/noomoo:architect` は意思決定記録、アーキテクチャスライス、データドキュメントを書きます。
4. **準備完了。** 準備完了ゲートが推測なしに実行可能と判断したときにだけ、タスクは作業に入ります。
5. **計画。** 実装計画はバージョン管理されたドキュメントで、コードを変える前にレビューと承認を受けます。
6. **デリバリー。** `/noomoo:task` はタスクを、テスト駆動の実装、レビュー、完全な検証を経て pull request まで運びます。
7. **レポート。** `/noomoo:report` は、発見事項や本番システムへの変更を証拠とともに記録します。

ドキュメントのテンプレートとレビュー基準はコアパッケージに同梱されています（`node_modules/noomoo/docs/`）。ドキュメントは正確な形を出力する `noomoo scaffold` で作成するため、名前・セクション・リンクは確認可能なまま保たれます。

## スキル

| スキル | 役割 |
|---|---|
| `/noomoo:start` | `noomoo next` をもとに、プロジェクトの現在地と次のステップを示します。 |
| `/noomoo:status` | プロジェクトのステータスを示します: ガード、最後のチェック、進行中の作業、対応が必要な項目。読み取り専用で、ステータスを描き直すために検証を実行することはありません。 |
| `/noomoo:doctor` | リポジトリ内の noomoo のインストールを確認します。読み取り専用で、セットアップ前でも動きます。 |
| `/noomoo:setup` | noomoo をリポジトリにインストールします: 計画を示し、同意を得てから適用します。 |
| `/noomoo:rollback` | マニフェストに基づいてインストールを元に戻します: 計画を示し、同意を得てから適用します。 |
| `/noomoo:validate` | `noomoo validate` でプロジェクトのドキュメントを確認します。何も書き込みません。 |
| `/noomoo:spec` | 新しい作業を、作り始める前に要件・ユースケース・機能・タスクとして記述します。 |
| `/noomoo:task <TASK-NNN>` | 1 つのタスクを、そのドキュメントから noomoo のゲートを経て pull request まで運びます。タスクのデリバリーの入口です。 |
| `/noomoo:architect` | 意思決定記録、アーキテクチャスライス、またはデータドキュメントを書きます。 |
| `/noomoo:intake` | 生の素材や転送されたメッセージを、オーナー向けの intake 提案にまとめます。 |
| `/noomoo:report` | 発見事項、または本番システムに加えた変更についてのレポートを、証拠とともに書きます。 |

## プラグインが実行するもの

スキルはプロジェクト自身のパッケージマネージャーでコアを実行し、決してダウンロードしません: `npx --no-install noomoo`、`pnpm exec noomoo`、`yarn exec -- noomoo`、`bun x --no-install noomoo`。パッケージがない場合、スキルはインストールを求めて停止します。

スキルはシェルコマンドもファイル変更も事前に許可しません。Claude Code はコアコマンドと編集のたびに確認を求めます。その確認画面から、プロジェクトに対してコマンドを許可できます。

プラグインには 2 つのフックがあります:

- **SessionStart** は `package.json` と `.noomoo/setup-manifest.json` だけを読みます。プロジェクトが noomoo を依存に含んでいるのに一度もセットアップされていない場合、`/noomoo:setup` の実行を促す 1 行のヒントを出力します。プロセスは起動しません。
- **PostToolUse**（`Edit` と `Write` が対象）は、3 つの条件がそろうまで何もしません。プロジェクトに `.noomoo/setup-manifest.json` があること、このリポジトリで noomoo を実行することに同意していること（セットアップが `~/.config/noomoo/trusted-repos.json` に記録）、コアがローカルにインストールされていることです。条件がそろうと、プロジェクトのパッケージマネージャー経由で `noomoo claude-hook-docs` を実行し、編集イベントを渡し、最大 20 秒待って、その出力をコンテキストとして Claude に返します。

どちらのフックも、パッケージのインストール、ネットワーク接続、信頼の記録は行いません。セットアップ、信頼、リポジトリのポリシーは、あくまで noomoo の明示的な操作です。明示的に承認された自動化では、`NOOMOO_TRUST_PROJECT=1` でプロジェクトの信頼を渡すこともできます。noomoo 自身がこの変数を設定することはありません。

プラグイン自体は Git にも GitHub にも何もインストールしません。セットアップを承認すると、コアが `.githooks/` に Git フックを追加することがあります（`pre-commit` と `pre-push` はドキュメントのチェックを実行し、`commit-msg` は AI の署名を拒否します）。noomoo がプロジェクトのフックを管理する場合、セットアップは `core.hooksPath` を noomoo が管理するフックディレクトリに設定することがあります。ユーザーが管理している既存のフック設定は、セットアップの所有ルールに従って保持されます。セットアップは GitHub Actions のワークフロー `.github/workflows/noomoo.yml` も追加します。GitHub のブランチ保護、Webhook、シークレットは変更しません。`/noomoo:rollback` はこれらをすべて取り除きます。

`/noomoo:task` は別のブランチで作業し、プロジェクトが求める場合は `.worktrees/` 配下の Git worktree で作業します。ブランチの push と pull request の作成は、明示的な許可を得てからしか行わず、マージは決して行いません。

## データとネットワークアクセス

- プラグインにはネットワークのコードもテレメトリーも含まれていません。公開版の noomoo コアパッケージにもテレメトリーの送信機能はありません。
- コアが書き込むのはリポジトリの中だけです: ドキュメント、設定、Git フック、CI ワークフロー、そして git で無視されるローカルのコマンドログ `docs/validation/events.jsonl`。セットアップは、作成するファイルをすべて書き込む前に示します。
- pull request、CI 実行、レビュアーの身元を読み取るコマンドは、あなたのトークンまたは `gh` のログインで GitHub API を呼び出します。
- モデルによるレビュー（`task-ready`、`plan-ready --judge`、`estimate`）は、あなたのマシンにインストールされた Claude CLI を読み取り専用のツールで起動し、レビュー対象のドキュメントのテキストを渡します。そのテキストは、あなた自身のアカウントと規約のもとで Claude の提供元に送られます。
- Git、`gh`、Claude Code は、それぞれ独自の認証とポリシーのもとで、それぞれのサービスと通信します。

## プラグインのインストール

このリポジトリのマーケットプレイスから、Claude Code にプラグインをインストールします:

```bash
/plugin install noomoo --marketplace TaskForceNow/noomoo
```

Claude Code が 2.1.275 より古い場合は、先にマーケットプレイスを追加します:

```bash
/plugin marketplace add TaskForceNow/noomoo
/plugin install noomoo@noomoo
```

Claude のプラグインディレクトリが利用可能になれば、それが 2 つ目の経路になります。

代替手段として、リリースのアーカイブを 1 セッションだけ読み込むこともできます。同じ noomoo の[リリース](https://github.com/TaskForceNow/noomoo/releases)から `noomoo-plugin-<version>.zip` と `SHA256SUMS` をダウンロードし、アーカイブを検証してから、それを指定して Claude Code を起動します:

```bash
shasum -a 256 -c SHA256SUMS --ignore-missing
claude --plugin-dir noomoo-plugin-<version>.zip
```

プロジェクトにインストールしたコアパッケージと同じリリースのプラグインアーカイブを使ってください。
